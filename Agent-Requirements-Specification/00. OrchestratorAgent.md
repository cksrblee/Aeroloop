# Agent_Requirements_Specification

### Agent Name
OrchestratorAgent

### Agent Overview
The `OrchestratorAgent` acts as the central router in the AeroLoop bidirectional LangGraph workflow. It evaluates the current global `WorkflowState` after any node execution and decides which agent should be invoked next, or if the workflow should terminate. It is responsible for handling downstream feedback (e.g., conflicting requirements) and routing the flow backwards to previous agents for resolution.

### Workflow Position
- **Upstream:** All worker agents (`MissionParsingAgent`, `CustomerRequirementAgent`, etc.)
- **Downstream:** All worker agents or `END` (termination).

### Functional Requirements
| ID | Requirement |
| --- | --- |
| ORC-FR-01 | The agent must evaluate the `WorkflowState` to determine the next node to execute. |
| ORC-FR-02 | The agent must route the workflow to `END` if all required stages are successfully completed. |
| ORC-FR-03 | The agent must route the workflow backwards (e.g., to Mission Parsing) if downstream agents report missing information or conflicting constraints in the `feedback_history`. |
| ORC-FR-04 | The agent must not execute domain-specific logic, but only routing logic. |

### Non-Functional Requirements
| ID | Requirement |
| --- | --- |
| ORC-NFR-01 | The routing decision must be deterministic based on the provided state fields (e.g., `status`, `next_node`, `errors`). |
| ORC-NFR-02 | The agent must prevent infinite loops by tracking the number of iterations or repeated feedback. |

### Input Specification
The agent accepts the global `WorkflowState`.
```json
{
  "user_input": "...",
  "mission_profile": {},
  "customer_requirements": [],
  "feedback_history": ["Missing payload info"],
  "current_node": "customer_requirement",
  "status": "error"
}
```

### Output Specification
The agent outputs an updated `WorkflowState` containing the explicit `next_node` routing directive.

### Tool and Knowledge Source Usage
None. The orchestrator may use an LLM if complex reasoning is needed to interpret feedback, but for standard deterministic routing, it relies on state variables.

### Reasoning and Decision Policy
- If `status == 'error'`, route to the node that can resolve the error based on `feedback_history`.
- If `status == 'success'`, route to the next logical stage in the standard sequence (Mission -> Customer Req -> Certification -> Config -> Simulation).
- If a downstream node explicitly sets `next_node`, honor that request unless it violates infinite loop constraints.

### Error Handling Policy
If the orchestrator cannot determine the next step or detects an infinite loop, it sets `status = 'failed'` and routes to `END`.

### Evaluation Criteria
| Metric | Description |
| --- | --- |
| Routing Accuracy | Agent correctly routes to the intended next step. |
| Loop Prevention | Agent terminates workflow if an infinite loop is detected. |

### Test Cases
- Normal flow: Mission -> Customer Req
- Error flow: Customer Req reports missing info -> Mission
