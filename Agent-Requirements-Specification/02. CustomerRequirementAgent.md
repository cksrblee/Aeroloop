# Agent_Requirements_Specification

### Agent Name
CustomerRequirementAgent

### Agent Overview
`CustomerRequirementAgent` analyzes the `MissionProfile` and generates candidate customer and operational requirements from the user’s mission intent.

### Workflow Position
- **Upstream**: `MissionParsingAgent`
- **Downstream**: `RequirementReasoningAgent`

### Functional Requirements

| ID | Requirement |
| --- | --- |
| CUST-FR-01 | The system shall receive a `MissionProfile` object as input. |
| CUST-FR-02 | The system shall generate customer requirement candidates (`CandidateRequirement`) based on explicit customer needs in the mission profile. |
| CUST-FR-03 | The system shall generate operational requirement candidates based on actual operational needs (e.g., reaching destination). |
| CUST-FR-04 | The system shall separate measurable, quantitative requirements from qualitative or preference-based requirements (soft objectives). |
| CUST-FR-05 | The system shall process ambiguous preferences by converting them to soft objectives, recording assumptions, or flagging them as needing clarification. |
| CUST-FR-06 | The system shall classify each requirement as `hard_constraint`, `soft_objective`, `report_only`, or `needs_clarification`. |
| CUST-FR-07 | The system shall specify the target for verification (`verification_target`) for each generated requirement. |
| CUST-FR-08 | The system shall assign a `priority` and `severity` for each generated requirement. |
| CUST-FR-09 | The system shall assign a `confidence` score (0.0 - 1.0) for each requirement candidate. |
| CUST-FR-10 | The system shall generate traceability evidence (`source_refs`, `rationale`) for each generated requirement. |
| CUST-FR-11 | The system shall generate clarification questions (`unresolved_questions`) for critical missing information in the mission profile. |
| CUST-FR-12 | The system shall output the final result in the predefined `CustomerRequirementResult` JSON format. |

### Non-Functional Requirements

| ID | Requirement |
| --- | --- |
| CUST-NFR-01 | **Schema-first Structure**: All outputs shall strictly adhere to predefined Pydantic schemas without relying on free-text output. |
| CUST-NFR-02 | **Hybrid Approach**: The system should prioritize a deterministic rule-based approach for explicitly parsed data, using LLM reasoning only as a supplementary aid for ambiguities and questions. |
| CUST-NFR-03 | **Prevent Hallucinations**: The system shall not assume or hallucinate numerical thresholds that are absent in the user input. |
| CUST-NFR-04 | **Separation of Concerns**: The system shall not directly process or generate certification or legal requirements (which is handled by `CertificationRequirementAgent`). |
| CUST-NFR-05 | **Reproducibility**: The system shall record agent version, config version, and model settings to ensure identical inputs result in identical outputs. |
| CUST-NFR-06 | **Low Temperature**: If using an LLM, the model temperature should be low (e.g., 0.1) to prioritize structured and reliable output over creativity. |
| CUST-NFR-07 | **Validatability**: The generated candidates shall be fully validatable against required fields (candidate_id, confidence range, operator/variable existence for hard constraints). |
| CUST-NFR-08 | **Extensibility**: The system's architecture should allow adding new requirement types (comfort, fleet_operation, etc.) with minimal changes. |
| CUST-NFR-09 | **Testability**: Individual requirement builders and generators shall be independently testable via unit tests. |
| CUST-NFR-10 | **Langfuse Integration**: The system shall support prompt versioning and operational tracing using Langfuse for experiment tracking and monitoring. |

### Tool and Knowledge Source Usage
- **Tools**: `CustomerRequirementBuilders` to deterministically apply logic based on the `MissionProfile`. LLM is reserved for fuzzy reasoning on remaining constraints.
- **Constraints**: Must NOT use external certification or airspace regulation databases, this is strictly translating the customer profile.

### Reasoning and Decision Policy
- **Deterministic First**: Always convert explicit measurements (e.g. `passenger_count`) to `hard_constraint` candidate requirements deterministically.
- **Fuzzy Preferences**: Vague preferences (e.g. noise constraint lists "low_noise") result in `soft_objective` candidates with stated system assumptions.
- **Missing Vital Information**: Missing information triggers `needs_clarification` requirements instead of hallucinating values.
- **Conflict Handling**: Resolving conflicts is out of scope; this agent merely translates the user intent as provided.

### Error Handling Policy
- If the `MissionProfile` lacks both `payload_kg` and `passenger_count`, flag a critical `unresolved_questions` requesting payload details.
- Outputs must be checked against `CustomerRequirementValidator`. If invalid candidates are produced, a `validation_errors_present` flag is added.

### Evaluation Criteria
| Metric | Description |
| --- | --- |
| Schema Validity | Output must pass Pydantic schema validation. |
| Evidence Alignment | Each generated requirement must be supported by mission input or system assumptions. |
| Hallucination Rate | Unmentioned attributes from the input should not result in hallucinated thresholds. |
| Validation Pass Rate | Internal `CustomerRequirementValidator` errors must be near zero. |

### Test Cases
- **Normal Case**: Provide `passenger_count=2`. Expect a capacity constraint requirement.
- **Missing-Information Case**: Provide `payload_kg=None`. Expect an unresolved question regarding payload.
- **Ambiguous-Input Case**: Provide `noise_constraints=["low_noise"]`. Expect a soft objective requirement with an assumption.
- **Edge Case**: Origin and Destination provided. Expect a `destination_reached` simulation requirement.
- **Invalid-Input Case**: Ensure certification requirements are not accidentally produced.
