# Agent_Requirements_Specification

### Agent Name
RequirementReasoningAgent

### Agent Overview
The `RequirementReasoningAgent` is responsible for merging requirements, detecting conflicts, and most importantly, resolving `unresolved_questions` and `needs_configuration_detail` generated by upstream agents (`CustomerRequirementAgent` and `CertificationComplianceAgent`). It queries the `KnowledgeBase` (ChromaDB) to ground its baseline assumptions and infer missing information based on domain context. This agent prevents workflow halts by providing aggressive baseline assumptions for completely underspecified prompts, while still logging its actions for human review.

### Workflow Position
- **Upstream:** `CustomerRequirementAgent`, `CertificationComplianceAgent`
- **Downstream:** `SizingAgent`, `GeometryDesignAgent`, `AerodynamicsAnalysisAgent`

### Functional Requirements
| ID | Requirement |
| --- | --- |
| RRA-FR-01 | The agent shall receive `RequirementReasoningInput` containing `mission_profile`, `candidate_requirements`, and `unresolved_questions`. |
| RRA-FR-02 | The agent shall detect duplicate or conflicting requirements and merge them. |
| RRA-FR-03 | The agent shall attempt to resolve each item in `unresolved_questions`. |
| RRA-FR-04 | The agent shall query the ChromaDB `KnowledgeBase` for contextual evidence to resolve missing or ambiguous parameters (e.g. standard payload weight). |
| RRA-FR-05 | The agent shall make conservative/baseline assumptions to fill missing gaps necessary for sizing and design. |
| RRA-FR-06 | The agent shall synthesize the final requirements into a high-level `ConceptBaseline` (SizingDraft) that defines macroscopic targets (range, payload, MTOW class, etc.) for direct use by the `SizingAgent`. |
| RRA-FR-07 | The agent shall output `RequirementReasoningResult` containing the `ConceptBaseline`, final refined requirements, resolved assumptions, and any remaining questions. |

### Non-Functional Requirements
| ID | Requirement |
| --- | --- |
| RRA-NFR-01 | The agent shall strictly output valid JSON matching the defined Pydantic schema. |
| RRA-NFR-02 | The agent shall not hide uncertainty; any assumption made must be explicitly recorded in `resolved_assumptions` with a confidence score and rationale. |
| RRA-NFR-03 | The agent shall not hallucinate precise mathematical certification rules if they cannot be found in the Vector DB. |

### Input Specification
```json
{
  "run_id": "RUN-001",
  "mission_profile": {
    "mission_type": "passenger_transport"
  },
  "candidate_requirements": [
    {
      "requirement_id": "REQ-01",
      "variable_name": "range_km",
      "threshold": 100
    }
  ],
  "unresolved_questions": [
    "What is the expected payload weight for a 4 passenger VTOL?"
  ]
}
```

### Output Specification
```json
{
  "run_id": "RUN-001",
  "status": "success",
  "concept_baseline": {
    "concept_id": "CONCEPT-001",
    "aircraft_type": "lift_cruise_vtol",
    "target_range_km": 100.0,
    "target_payload_kg": 400.0,
    "battery_reserve_percent_target": 20.0,
    "assumptions": ["100kg per passenger payload"]
  },
  "final_requirements": [
    {
      "requirement_id": "REQ-01",
      "variable_name": "range_km",
      "threshold": 100
    },
    {
      "requirement_id": "REQ-02",
      "variable_name": "payload_kg",
      "threshold": 400
    }
  ],
  "resolved_assumptions": [
    {
      "question": "What is the expected payload weight for a 4 passenger VTOL?",
      "assumed_value": "400 kg",
      "rationale": "Assuming 100kg per passenger including luggage as a standard baseline based on retrieved evidence.",
      "confidence": 0.85
    }
  ],
  "remaining_unresolved_questions": [],
  "conflicts_detected": []
}
```

### Tool and Knowledge Source Usage
- **KnowledgeBase (ChromaDB)**: Queried for keywords present in `unresolved_questions` (e.g. "payload passenger VTOL") to retrieve past examples or regulations.

### Reasoning and Decision Policy
1. For every unresolved question, retrieve top-K similar documents from ChromaDB.
2. If evidence strongly supports a standard value (e.g. 100kg/pax), adopt it as an assumption.
3. If no evidence exists, apply an aggressive industry-standard baseline (e.g. typical small VTOL parameters) but flag it with low confidence (<0.5).
4. Do not pause the workflow unless explicitly instructed. Translate assumptions into new or updated `FinalRequirement` items.

### Error Handling Policy
- If LLM parsing fails, retry once. If it fails again, fallback to returning the original candidate requirements with an empty `resolved_assumptions` list.
- If ChromaDB connection fails, proceed with reasoning without DB evidence and log a warning.

### Evaluation Criteria
| Metric | Description |
| --- | --- |
| Schema Validity | JSON output matches schema. |
| Resolution Rate | Percentage of `unresolved_questions` answered via `resolved_assumptions`. |
| Hallucination Rate | Assumptions lack rationales or fabricate non-standard baselines. |

### Test Cases
- **Normal Case**: Provide `unresolved_questions` about payload. Agent resolves it using DB context.
- **Conflict Case**: Provide two conflicting requirements (e.g. max range = 100km, max range = 50km). Agent resolves conflict and documents rationale.
