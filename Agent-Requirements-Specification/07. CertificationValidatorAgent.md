# Agent_Requirements_Specification

### Agent Name
CertificationValidatorAgent

### Agent Overview
The `CertificationValidatorAgent` acts as a deterministic "inspector" in the AeroLoop workflow. It receives the `ConceptBaseline` (SizingDraft) generated by the `RequirementReasoningAgent` and the `ComplianceChecklistItem`s (CCL) extracted by the `CertificationComplianceAgent`. It performs rule-based checks to ensure the baseline numerical targets (e.g., reserve battery, payload, noise level) do not violate the established certification rules before allowing the design to proceed to the sizing stage.

### Workflow Position
- **Upstream:** `RequirementReasoningAgent` (provides `ConceptBaseline`), `CertificationComplianceAgent` (provides `ccl_items`)
- **Downstream:** `SizingAgent`

### Functional Requirements
| ID | Requirement |
| --- | --- |
| CVA-FR-01 | The agent shall receive a `CertificationValidationInput` containing a `ConceptBaseline` and a `CertificationComplianceResult`. |
| CVA-FR-02 | The agent shall parse the numerical parameters of the `ConceptBaseline` (e.g., target range, reserve battery, payload). |
| CVA-FR-03 | The agent shall compare the `ConceptBaseline` parameters against the constraints defined in the `ccl_items`. |
| CVA-FR-04 | The agent shall output a `CertificationValidationResult` detailing whether the baseline is valid, along with any violations or warnings. |

### Non-Functional Requirements
| ID | Requirement |
| --- | --- |
| CVA-NFR-01 | The agent shall operate deterministically. It should rely on strict logical rule-checking rather than probabilistic LLM generation for numerical limits. |
| CVA-NFR-02 | The agent shall execute in under 1 second. |
| CVA-NFR-03 | The agent must accurately flag non-compliant designs to prevent downstream simulation failures. |

### Input Specification
```json
{
  "run_id": "RUN-001",
  "concept_baseline": {
    "concept_id": "CONCEPT-001",
    "target_payload_kg": 400.0,
    "battery_reserve_percent_target": 15.0
  },
  "compliance_result": {
    "ccl_items": [
      {
        "topic_area": "energy reserve",
        "compliance_status": "planned"
      }
    ]
  }
}
```

### Output Specification
```json
{
  "validation_id": "VAL-12345678",
  "run_id": "RUN-001",
  "is_valid": false,
  "violations": [
    "Battery reserve target (15.0%) is below the minimum required SC-VTOL margin of 20%."
  ],
  "warnings": [],
  "status": "failed"
}
```

### Tool and Knowledge Source Usage
- Does not require external LLM calls or ChromaDB retrievals. It uses the input payloads directly.

### Reasoning and Decision Policy
1. Evaluate `baseline.battery_reserve_percent_target`. If < 20%, raise a violation.
2. Evaluate `baseline.target_payload_kg`. If > 5000kg, raise a warning for category limits.
3. If any violations exist, set `is_valid = false` and `status = failed`.
4. If no violations exist, set `is_valid = true` and `status = success`.

### Error Handling Policy
- If `concept_baseline` is missing required fields, generate a warning and assume worst-case (or prompt for human review).
- If the agent fails to execute, it must return a failed status so the orchestrator halts the process.

### Evaluation Criteria
| Metric | Description |
| --- | --- |
| Schema Validity | JSON output matches the `CertificationValidationResult` schema. |
| Determinism | The exact same input must always produce the exact same violations/warnings list. |
| Catch Rate | Known violations in test cases must be caught 100% of the time. |

### Test Cases
- **Valid Case**: `battery_reserve_percent_target = 25.0`. Agent returns `is_valid = true`.
- **Invalid Case**: `battery_reserve_percent_target = 10.0`. Agent returns `is_valid = false` with a violation.
- **Missing Field Case**: `battery_reserve_percent_target = null`. Agent returns `is_valid = true` but appends a warning about high risk due to missing specification.
