# Agent_Requirements_Specification

### Agent Name
MissionParsingAgent

### Agent Overview
The `MissionParsingAgent` is responsible for parsing a natural language mission description provided by the user and converting it into a fully structured `MissionParsingResult`.

### Workflow Position
- **Upstream**: User Interface (raw text input)
- **Downstream**: `CustomerRequirementAgent`, `AirspaceEnvironmentAgent`, `CertificationRequirementAgent`

### Functional Requirements

| ID       | Requirement                                                                                                                          |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| MP-FR-01 | The system shall extract the operation area, departure point, destination, and mission type from the natural-language mission input. |
| MP-FR-02 | The system shall extract transportation-related information such as number of passengers, payload, and cargo conditions.             |
| MP-FR-03 | The system shall extract numerical conditions such as altitude, distance, speed, time, battery, and noise.                           |
| MP-FR-04 | All numerical conditions shall be normalized based on SI units.                                                                      |
| MP-FR-05 | The system shall distinguish between explicit constraints and candidate implicit constraints.                                        |
| MP-FR-06 | The system shall record missing required information as `MissingField`.                                                              |
| MP-FR-07 | Ambiguous expressions shall be recorded as `Ambiguity` objects.                                                                      |
| MP-FR-08 | The system shall not generate information that is not present in the user input as if it were a confirmed value.                     |
| MP-FR-09 | Each extracted field shall include an evidence span from the original input.                                                         |
| MP-FR-10 | Each parsing result shall include a confidence score.                                                                                |
| MP-FR-11 | The system shall generate `Requirement Seed` data that can be used by downstream requirement agents.                                 |
| MP-FR-12 | Conditions that can be converted into Runtime Verification shall be linked to candidate simulation variables.                        |
| MP-FR-13 | The parsing result shall be structured as JSON that can be stored in the Blackboard.                                                 |
| MP-FR-14 | Fields with parsing failures or high uncertainty shall return `null` together with a reason.                                         |
| MP-FR-15 | The system should be designed to process both Korean and English inputs.                                                             |

### Non-Functional Requirements

| ID        | Requirement                                                                                                      |
| --------- | ---------------------------------------------------------------------------------------------------------------- |
| MP-NFR-01 | The output shall always follow the predefined JSON Schema.                                                       |
| MP-NFR-02 | The system shall return results as consistently as possible for the same input.                                  |
| MP-NFR-03 | Numerical conditions shall be normalized to a level that can be directly used by downstream calculation engines. |
| MP-NFR-04 | Missing information and assumptions shall be clearly distinguished.                                              |
| MP-NFR-05 | The parsing result shall be easy for humans to review.                                                           |
| MP-NFR-06 | Field names shall remain stable so that downstream agents can reuse them.                                        |
| MP-NFR-07 | Conservative `null` handling shall be prioritized over incorrect inference.                                      |
| MP-NFR-08 | The parsing result shall include evidence from the original input to support Traceability Matrix generation.     |

### Input Specification
**Input Name**: `MissionParsingInput`
**Description**: Contains the raw natural language mission text.
**Schema**:
```json
{
    "mission_id": "string",
    "raw_user_input": "string",
    "language": "string (default 'ko')",
    "user_context": "dict | null",
    "default_unit_system": "string (default 'SI')",
    "project_context": "dict | null"
}
```

### Output Specification
**Output Name**: `MissionParsingResult`
**Description**: A structured profile containing parsed fields, explicit constraints, implied candidates, ambiguities, missing fields, requirement seeds, and monitoring candidates.
**Schema**:
```json
{
    "mission_id": "string",
    "raw_input": "string",
    "mission_profile": "MissionProfile",
    "explicit_constraints": ["ParsedConstraint"],
    "implicit_constraint_candidates": ["ParsedConstraint"],
    "missing_fields": ["MissingField"],
    "ambiguities": ["Ambiguity"],
    "assumptions": ["Assumption"],
    "evidence_spans": ["EvidenceSpan"],
    "requirement_seed_candidates": ["RequirementSeed"],
    "runtime_monitoring_candidates": ["RuntimeMonitoringCandidate"],
    "confidence_summary": "ConfidenceSummary"
}
```

### Tool and Knowledge Source Usage
- **Tools**: LLM for text parsing and extraction.
- **Constraints**: No external tools like web search or DB retrieval are used by this agent.

### Reasoning and Decision Policy
- **Extraction vs Generation**: The agent must extract information, not invent it. Missing information must be flagged as `MissingField` rather than assumed.
- **Ambiguity Handling**: Vague statements (e.g., "fast") must be flagged as an `Ambiguity` rather than definitively resolved.
- **Traceability**: Every extracted fact or constraint must be linked to an `EvidenceSpan`.

### Error Handling Policy
- If critical fields are entirely unparseable, record as `MissingField`.
- If the LLM output violates schema, the wrapper must attempt retry or fallback to an empty/error result.
- Return `null` with a reason for fields with high uncertainty.

### Evaluation Criteria
| Metric | Description |
| --- | --- |
| Schema Validity | Output must pass Pydantic schema validation. |
| Hallucination Rate | Extracted facts must not contain values not present in the input. |
| Consistency | Similar inputs should yield identical `MissionProfile` field mappings. |
| Completeness | All explicit constraints in text must have a corresponding `RequirementSeed`. |

### Test Cases
- **Normal Case**: A well-structured paragraph with distance, speed, passengers. (Expect full extraction).
- **Missing Info Case**: Only origin and destination provided. (Expect `MissingField` for payload/passengers).
- **Ambiguous Input Case**: "Fly safely to campus". (Expect `Ambiguity` and soft constraint seeds).
- **Invalid Input Case**: Gibberish text. (Expect graceful fallback and missing fields).
