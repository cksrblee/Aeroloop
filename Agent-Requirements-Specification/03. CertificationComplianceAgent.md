# Agent_Requirements_Specification

### Agent Name
CertificationComplianceAgent (or CertificationBasisAndComplianceAgent)

### Agent Overview
The `CertificationComplianceAgent` acts as a "Regulation-to-Design Compiler" (an early certification planning generator). It takes the `MissionProfile`, `CustomerRequirement`, and the preliminary `AircraftConcept` to identify applicable certification standards for UAM/eVTOL designs. From a Type Certificate (TC) preparation perspective, it generates a preliminary **Compliance Checklist (CCL)** and **Means of Compliance (MoC)** plan. Instead of merely retrieving regulations, it determines "which clauses to include/exclude and how to demonstrate compliance for each."

This agent enables early risk assessment by passing the CCL and MoC to AeroLoop's simulation and Runtime Verification stages, allowing the platform to evaluate compliance risks through low-fidelity analysis and 3D simulation before expensive traditional testing.

### Workflow Position
This agent should ideally be invoked twice, depending on the maturity of the design:
- **First Invocation (Requirements Analysis Phase)**
  - **Input:** `MissionProfile`, `CustomerRequirement`
  - **Output:** Certification Basis candidates, initial CCL, initial MoC candidates (many items may be marked `tbd` due to lack of design specifics).
- **Second Invocation (Post-Configuration Design Phase)**
  - **Input:** `AircraftConcept` (detailed with propulsion architecture, number of engines/motors, lift units, etc.)
  - **Output:** Updated CCL (applicability resolved), refined MoC plan, updated certification risk.

### Functional Requirements
| ID | Requirement |
| --- | --- |
| CCA-FR-001 | The agent must accept `MissionProfile` and `CustomerRequirement` as inputs. |
| CCA-FR-002 | The agent must query against three regulatory axes: SC-VTOL Small, Small Rotorcraft, and Small Aircraft. |
| CCA-FR-003 | The agent must generate Certification Basis candidates. |
| CCA-FR-004 | The agent must retrieve relevant clauses from the Certification DB. |
| CCA-FR-005 | The agent must determine the applicability of each retrieved clause based on the aircraft concept and mission. |
| CCA-FR-006 | The agent must convert applicable clauses into Compliance Checklist (CCL) Items. |
| CCA-FR-007 | The agent must map proposed Means of Compliance (MoC) methods to each CCL Item. |
| CCA-FR-008 | Each CCL Item must have an applicability status: `included`, `excluded`, `not_applicable`, `tbd`, or `requires_human_review`. |
| CCA-FR-009 | The agent must generate trace links connecting customer requirements to their corresponding CCL Items. |
| CCA-FR-010 | Items that cannot be evaluated due to insufficient design information must be recorded in `unresolved_questions`. |
| CCA-FR-011 | High-risk items such as one-engine-out, emergency operation, and energy reserve must be flagged. |
| CCA-FR-012 | The agent must indicate which MoCs can be preliminarily supported via simulation in the PoC. |
| CCA-FR-013 | The final output must conform to the `CertificationComplianceResult` JSON schema. |

### Non-Functional Requirements
| ID | Requirement |
| --- | --- |
| CCA-NFR-001 | The agent must solely rely on the provided Certification DB and must not fabricate clause numbers (`hallucinated_clause_count` = 0). |
| CCA-NFR-002 | The output must strictly pass Pydantic/JSON schema validation. |
| CCA-NFR-003 | All CCL Items must include a source document, clause ID, and rationale. |
| CCA-NFR-004 | All MoC Plans must explicitly state their limitations. |
| CCA-NFR-005 | The agent must present its output as a preliminary planning tool, not as a final certification or legal judgment. |
| CCA-NFR-006 | Items requiring domain expert input must be flagged as `requires_human_review`. |
| CCA-NFR-007 | The agent must produce reproducible results given the same input and DB version. |
| CCA-NFR-008 | Langfuse traces must capture `prompt_version`, `db_version`, `source_family`, and `retrieved_clause_ids`. |
| CCA-NFR-009 | The agent must support a mode where sensitive certification/design documents are not fully exposed to external LLMs. |
| CCA-NFR-010 | The agent must not frame its output as actual certification approval. |

### Input Specification
**1. CertificationComplianceInput**
- `run_id` (str)
- `mission_profile` (MissionProfile)
- `customer_requirements` (list[CandidateRequirement])
- `aircraft_concept` (AircraftConcept | None) - Can be None during the first invocation.
- `jurisdiction_hint` (Literal["EASA", "FAA", "KAS", "AUTO"])
- `certification_source_policy` (CertificationSourcePolicy): Must enforce `strict_db_only=True`.

**2. AircraftConcept**
- Includes design specifics such as MTOW, passenger count, propulsion type (electric, hybrid, etc.), number of engines/motors, VTOL capability, and intended operations.

### Output Specification
**1. CertificationComplianceResult**
- `certification_basis_candidates`: List of considered certification standards (e.g., SC-VTOL-001).
- `ccl_items`: The status of each clause (`included`, `excluded`, `tbd`), risk level, and requirement mapping (`ComplianceChecklistItem`).
- `moc_plans`: Proposed methods to demonstrate compliance (`MeansOfCompliancePlan`), including `poc_support_level`.
- `requirement_links`: Traceability mapping between customer requirements and CCL items.
- `conflicts`: Identified conflicts between design constraints and certification requirements.
- `quality_report`: Summary statistics such as processed CCL count and simulation-supported MoC count.

### Internal Module Structure & Agent Flow
To prevent overwhelming a single LLM call, this agent is decomposed into multiple deterministic modules combined with LLM reasoning.

**CertificationComplianceAgent Flow**
```text
CertificationComplianceAgent
├── CertificationBasisSelector
├── ClauseRetriever
├── ApplicabilityAssessor
├── ComplianceChecklistBuilder
├── MoCMapper
├── CertificationRiskAssessor
└── TraceabilityLinker
```

**1. CertificationBasisSelector**
- **Inputs:** `MissionProfile`, `CustomerRequirement[]`, `AircraftConcept`
- **Outputs:** `CertificationBasisCandidate[]`
- **Role:** 
  - If VTOL, propose `SC-VTOL Small` as primary.
  - If rotorcraft-like, propose `Small Rotorcraft` as secondary.
  - If wing-borne cruise is present, propose `Small Aircraft` as secondary.
  - If uncertain, record in `unresolved_questions`.

**2. ClauseRetriever**
- **Inputs:** `CertificationBasisCandidate[]`, `topic_area`, `keywords`
- **Outputs:** `CertificationClause[]`
- **Search Targets:** `SC-VTOL Small`, `Small Rotorcraft`, `Small Aircraft`
- **Search Topics:** `performance`, `flight`, `controllability`, `structures`, `propulsion`, `energy_storage`, `systems_and_equipment`, `occupant_safety`, `operating_limitations`, `continued_airworthiness`, `emergency_operation`, `noise`

**3. ApplicabilityAssessor**
- **Inputs:** `CertificationClause[]`, `MissionProfile`, `AircraftConcept`
- **Outputs:** `ComplianceChecklistItem[]` (with applicability status)
- **Status Options:** `included`, `excluded`, `not_applicable`, `tbd`, `requires_human_review`

**4. ComplianceChecklistBuilder**
- **Role:** 
  - Convert applicable clauses into `CCL Item`s.
  - Link with `related_customer_requirement_id` and mission fields.
  - Assign initial `risk_level` and `compliance_status`.

**5. MoCMapper**
- **Role:** Assign potential Means of Compliance (MoC) for each CCL item.
- **Default Mapping Examples:**
  | Topic Area | Default MoCs |
  | --- | --- |
  | `performance` | `engineering_analysis`, `simulation`, `flight_test` |
  | `controllability` | `simulation`, `flight_test` |
  | `structures` | `engineering_analysis`, `ground_test` |
  | `propulsion` | `engineering_analysis`, `ground_test`, `flight_test` |
  | `energy_storage` | `engineering_analysis`, `ground_test` |
  | `systems_and_equipment` | `design_review`, `software_verification`, `safety_assessment` |
  | `operating_limitations` | `design_review`, `simulation` |
  | `emergency_operation` | `safety_assessment`, `simulation`, `flight_test` |
  | `occupant_safety` | `design_review`, `ground_test`, `inspection` |
  | `noise` | `analysis`, `simulation`, `flight_test` |

### Tool and Knowledge Source Usage
- **Certification DB**: The agent must query the database across the following three axes:
  1. `SC_VTOL_SMALL`: VTOL-capable aircraft small category (e.g., EASA SC-VTOL Issue 2).
  2. `SMALL_ROTORCRAFT`: Small Helicopter (e.g., EASA CS-27, FAA Part 27).
  3. `SMALL_AIRCRAFT`: Normal-category Aeroplanes (e.g., EASA CS-23, FAA Part 23).
- **No Hallucination**: Clauses not explicitly found in the DB must not be fabricated; they must be excluded or flagged as unresolved.

### Reasoning and Decision Policy
- **Applicability Assessment**:
  - `included`: Clearly applies to the aircraft concept.
  - `excluded`: The design characteristics allow exemption.
  - `not_applicable`: Irrelevant to the concept.
  - **(Crucial)** If the aircraft geometry or architecture is ambiguous, do not blindly exclude. Mark as `tbd` or `requires_human_review`.
- **MoC Determination**:
  - Emphasize identifying items that can be evaluated via **engineering_analysis** or **simulation** as Preliminary Evidence in the PoC, rather than jumping straight to expensive traditional tests (e.g., flight tests).
  - Prioritize CCL items that can be linked to Runtime Verification (e.g., operating limitations, flight performance, energy reserves).

### Error Handling Policy
- If the LLM attempts to reference regulations outside the database (violating `strict_db_only=True`), the system must filter them out or raise an error.
- Having a large number of `tbd` items due to missing aircraft concept data is not an error; it acts as a trigger for the second invocation (reflected in the `readiness_level` of the `quality_report`).

### Evaluation Criteria (Score / Langfuse)
This agent will be traced in Langfuse under `trace.name = certification-compliance-analysis` and evaluated on:
- `schema_validity`: JSON output validity.
- `db_groundedness`: Reliance solely on retrieved DB content.
- `hallucinated_clause_count`: **Must be 0.**
- `human_review_item_count`: Number of items flagged for expert review.
- `simulation_supported_moc_count`: Number of MoCs that can be routed to 3D Simulation/Runtime Monitor.
- `traceability_coverage_ratio`: Ratio of customer requirements mapped to CCL items.

### Test Cases
- **Initial Invocation (Missing Concept)**: Call without `AircraftConcept`. Ensure propulsion-related items (like OEI) are correctly marked as `tbd`.
- **Second Invocation (Post-Design)**: Supply Distributed Electric Propulsion data. Verify that OEI-related CCL states are updated accordingly.
- **Runtime Verification Linkage**: Ensure CCL items related to `Operating limitations` map to a `simulation` MoC, demonstrating integration with the PoC simulation.
